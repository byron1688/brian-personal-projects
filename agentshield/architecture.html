AgentShield · reference design

AgentShield for chatbot agents in the cloud

By Brian ChenThe source code is confidential and not intended to be shared.

A chatbot agent in the cloud is more than a model call. It reads web pages, searches a knowledge base, calls company APIs, and runs as containers next to customer data. This page shows such a system, where AgentShield's defense layers go, and how each layer works inside. AWS is the example; the same design maps to Google Cloud and Azure.

  • Every pathOne checkpoint per way in or out

    Model calls, tool calls, the way out to the internet and the way into the knowledge base each pass through one gateway that checks them.

  • D2 · ExecutionApproved where the tool runs

    Risky tools wait for a person, who sees the exact arguments. Each approval works once, for that call only.

  • D3 · EgressThe address, not the URL

    The proxy resolves names itself and connects only to the address it checked, so cloud credentials, internal hosts and DNS tricks stay out of reach.

  • D4 · KnowledgeSealed, per-user knowledge

    Documents are checked before indexing and every chunk is sealed. Search returns only chunks the signed-in user may read.

  • D6 · ContainmentOne kill switch, everywhere

    Kill, quarantine and approvals live in one shared store, so every gateway server and the egress proxy agree at once.

  • D7 · EvidenceA record nobody can quietly change

    Hash-chained audit records go to a write-once archive, and every admin action names the person who took it.

Part 1 · Identify

The system we protect

A customer-support chatbot built as an agent. Claude decides which tools to call; the app executes them through three MCP servers: web search, RAG over a LanceDB knowledge base, and internal company APIs. Everything runs as containers on ECS Fargate. Nothing here is defended yet beyond the usual cloud controls.

MCP servers run as separate ECS services (Streamable HTTP) LanceDB is embedded in the RAG MCP; tables live on S3 Query and document embeddings come from Bedrock Chat history in DynamoDB; sign-in through Cognito

Part 3 · D1 up close

The LLM gateway, component by component

D1 handles one thing: every call between the agent app and the model. It sees the full context the app sends (user messages, history, tool definitions, tool results) and everything the model sends back (text and the tools it wants to call). It does not see a tool actually running; that is D2. The four lines in the diagram summarize twelve components. Most exist today; the new work is what it takes to sit in front of Claude.

One request, in order

① Inbound adapter→③ Admission→④ Routing + provider→ ⑤ Input screening→⑥ Context assembly→⑧ Server-tool policy→ ⑦ Model call→⑨ Output checks→⑩ Tool-call governance→ ⑪ Containment→⑫ Observability→② Streaming reply

Blue outline: the parts specific to Claude. Open any row for what it does, why it exists and how it works.

One conversation format inside the gateway

Translating Claude requests into OpenAI's format and back would lose thinking blocks, cache markers and citations, and would change bytes the model already saw. Instead both protocols map into one internal format (the IR) that holds only what security checks need. Everything else is carried untouched: blocks the gateway does not change are written back byte for byte.

ConceptOpenAI Chat CompletionsInternal format (IR)Anthropic Messages

Claude's thinking and the rule of never editing history

Claude's newest models sign every thinking block with a record of everything before it: the top-level system prompt, the set of tools, every earlier message, and the model. When the history comes back, the API checks that record. Appending is fine. Rewriting, deleting or inserting anything the model has already seen invalidates the thinking after that point and, by default, fails the request with a 400. In one line: what the model has seen must come back identical.

What D1 changesConflict?How D1 stays safe

So in normal operation the gateway's checks and Claude's thinking do not collide. The one real conflict is a message that went to the model unchanged earlier and is flagged only now, for example after a rule update mid-conversation.

Credentials

The app's Claude SDK changes two values: base_url points at the gateway and the key becomes a gateway key. The Anthropic key lives only in a secret the gateway task can read; Bedrock uses the gateway task's IAM role, limited to invoking the chosen models. The app's role cannot read either.

Part 4 · D6 up close

Shared security state, so every gateway task agrees

D1, D2 and D7 make containment decisions: stop the service, quarantine a caller, cap a quota, trip a breaker, approve a tool call once. Those decisions only hold if every gateway task sees them and they survive a restart. D6 moves them out of process memory into one store: SQLite on a laptop, DynamoDB on AWS. It adds no box to the request path; it is the memory the other layers share.

What breaks without it

An operator presses the kill switch on task AB keeps servingEvery task checks the switch at admission and again before release
An approval is created on A; the operator's decision lands on BB has never heard of itOne approval record, reachable from any task
The same approved call arrives on A and B at onceBoth release itA conditional write marks it used; only one succeeds
60 requests per minute, two tasks120 in practiceOne shared counter
A deploy replaces every taskQuarantines, breaker counts and approvals resetNothing resets

Two ideas that keep it correct

Design
  1. Actions, not reads and writes. The store exposes operations such as consume_approval or hit_rate, each atomic on its own. Nothing reads a record, changes it in Python and writes it back, so two tasks cannot overwrite each other.
  2. Versions instead of edits. Every approval records the kill-switch version and its principal's version when it was created, and is usable only while both still match. Pressing the kill switch, or quarantining a caller, voids every earlier approval at once, even after a resume, without touching each record. Requests do the same: a snapshot at admission and another before release; if a version moved, the answer is withheld.

Three backends, one contract

One DynamoDB table holds everything, keyed by namespace and principal: the control item, each principal's containment item, rate and breaker buckets, replay fingerprints and approvals. TTL only cleans up; expiry is always checked from timestamps, because DynamoDB may delete an expired item days later. The same contract tests run against all three backends.

When the store is down

Refuse with 503, in enforce and monitor mode alike. Falling back to an empty in-memory state would quietly lift every quarantine and the kill switch. /readyz reports the store's health, so the load balancer stops sending traffic to a task that cannot reach it.

What D6 does not do

  • Take back output already sent. Between the last check and release there is still a very short gap.
  • Stop a stream on another task instantly. A kill on task B reaches task A at A's next check, before release.
  • Guarantee a tool runs once. Single use means the call is released once; the executor (D2) still needs its own idempotency.
  • Merge audit chains. Each task writes its own chain; D7 archives every chain, write-once, in one bucket.
Part 5 · D2 up close

The MCP gateway, where tools actually run

D1 sees the tool calls the model proposes. D2 sees the calls the app actually makes, the tool definitions each MCP server declares, and the results before the app reads them. The app no longer talks to the three MCP servers; it calls POST /mcp/<server> on the gateway, and network rules (D5) make the gateway the only way through.

Why the protocol version matters

MCP 2026-07-28 is stateless: no handshake, no session ID, every request a separate POST that carries its own protocol version. The method, the tool name and selected arguments are mirrored into headers, and anything that reads those headers must reject a request whose headers and body disagree. That lets the gateway judge each call on its own. For servers that still need the older initialize handshake, the gateway performs it upstream and stays stateless toward the app.

Tool poisoning and rug pulls

A tool's description goes into the model's context, so a hostile or compromised server can hide instructions there, or ship a harmless version for review and change it later. Each allowed tool can carry a pin: a hash of its whole definition. agentshield mcp pins <server> prints the current pins for an operator to review and paste into the profile. A definition that no longer matches is hidden from tools/list and refused at tools/call. That is the server's fault, not the caller's, so it alerts once and never feeds the caller's circuit breaker.

What D2 does not do

  • See inside an MCP server: what it reaches on its own is for D3 (egress) and D5 (least privilege).
  • Help if the app can bypass it: only the gateway may reach the MCP servers, enforced by the network.
  • Check images or audio: dropped by default.
  • Relay resources, prompts, subscriptions or input requests: each would need its own checks, so they are refused.
  • Approve twice: tools that run through D2 are approved at D2, where the real arguments are known, and D1 only checks their shape.
Part 6 · D3 up close

The egress proxy: who may connect where

D1 and D2 judge content. A steered model can still ask a tool to fetch http://169.254.169.254/, an internal admin page, or an attacker's URL with customer data in the query string. Those have to be stopped where the network connection is made, by looking at the address actually reached. Every service that needs the internet sets HTTPS_PROXY to D3, and security groups make it the only way out.

Why a small upload cap matters

A page fetch sends little and receives a lot. Capping what each connection may send (64 KiB by default) limits how much a steered tool can carry out in one go, and each attempt leaves a record. Services that legitimately send large requests, such as the gateway calling the Claude API, get a larger cap.

What D3 does not do

  • See HTTPS paths or content: it does not decrypt. D2 checks what tools return.
  • Stop data hidden in DNS lookups: tasks resolve names without the proxy. DNS Firewall applies per VPC, so the proxy sits in its own egress VPC and the workload VPC resolves only AWS and internal names (D5).
  • Match a tunnel's TLS server name to the name it asked for: it guarantees the address reached, not the application behind it.
  • Stop misuse of an allowed host: data placed in search queries to an allowed API. Upload caps reduce the volume; D1 and D2 check the arguments.
  • Replace network enforcement: without security groups or Network Firewall, a service that ignores the proxy goes straight out.
Part 7 · D7 up close

Security operations: see it, act on it, prove it later

D1 to D3 make decisions and D6 shares them. D7 gets those decisions to people and keeps a record nobody can quietly change: alerts reach whoever is on call, audit records land in a write-once archive, and every admin action is made by a named person with a role.

Where events go

SinkReceivesBehavior
1audit_fileEvery decisionThe local hash chain; required, cannot be turned off
2logAudit records and alertsJSON lines on standard output for CloudWatch Logs; with metrics, CloudWatch Embedded Metric Format turns counts by event type into metrics with no API call
3sns, webhookAlertsEach has its own minimum severity. The same alert from the same principal goes out once a minute and the next one carries the count; approval requests and kill switch changes always go out
4s3_archiveThe audit fileNew complete lines every minute and at shutdown, one object per segment, checked against the chain before upload; S3 Object Lock keeps each segment for its retention period

A sink never changes a decision. Delivery runs in the background; a failing sink is counted in /admin/status and the request carries on.

Why the archive matters

A local hash chain notices one edited record, but not a deleted file, and an ECS task's disk disappears when the task is replaced. Segments in an Object Lock bucket survive both. agentshield audit verify-archive checks every chain: the records in each segment, consecutive segment numbers, and each segment starting where the previous one ended. Object Lock protects object versions, not names, so each segment is written once and only if its key is new, and the check reads every version: a segment that gained a second version or a delete marker fails, and the first version is the record. What it cannot cover is the last minute before a task is compromised, which has not been uploaded yet.

Who may do what

RoleCan
VviewerStatus, pending approvals, alerts, audit, the console
AapproverAlso approve or deny a held tool call
OoperatorAlso kill and resume, quarantine and release, revoke approvals

People sign in through the load balancer's OIDC login. The gateway checks the ALB's ES256 signature, that the configured ALB signed it, and that it has not expired, then grants roles by email or group from agentshield.yaml. Audit records and approvals carry the person's email. Changes from a browser session must send a header a cross-site form cannot set. The old admin token stays as break-glass with every role, and each change made with it raises an alert.

Part 8 · D4 up close

The knowledge base: checked on the way in, filtered on the way out

Every chunk the RAG server returns lands in the model's context word for word. A poisoned wiki page answers every future question with the attacker's text, and a search that ignores permissions shows salary bands to a sales agent. D4 checks each document once, before it is embedded, and checks each chunk again, against the signed-in user, before the agent reads it.

On the way in: agentshield ingest scan

StepWhat happens
1What a reader seesOnly visible text is kept. Hidden elements, white or zero-size text, off-screen text and comments are set aside; Unicode tag characters are decoded to the ASCII they hide; zero-width characters go; text is normalized so full-width letters read as plain ones
2CheckThe profile's own modules read the document as untrusted data, custom ones included. Instructions in the visible text, anything at all in the hidden text, tag characters, or a document with no groups: quarantine, with reasons and no copy of the text
3CleanSecrets and ID numbers are redacted; the document is kept
4SealEach chunk carries its source, the groups allowed to read it and an HMAC seal over all of it; only the ingestion job and the gateway hold the key
5RecordOne audit record per document through the D7 sinks, and one alert per run when anything was held

On the way out: the RAG search tool through D2

CheckResult
1Who is askingThe user's JWT is verified against the identity provider's keys; approvals and cached tool lists follow the verified user, and the RAG server receives the verified user and groups
2First filter, in the RAG serverA LanceDB prefilter so the search only ranks chunks the user may read

What D4 cannot do

  • Catch text that is wrong but looks normal ("refunds within 365 days"). That needs review of who may publish.
  • Fix wrong permissions given at ingestion: it enforces the groups it is told.
  • Protect retrieval the app does itself and pastes into the prompt; that path only gets D1's input checks.
Part 9 · Framework

How the code is organized

Every layer is built on the same pipeline. A request arrives through an adapter, passes the core's mandatory controls and a set of pluggable defense modules, is acted on by rules set per profile, goes to a model through a provider, and every event goes to pluggable sinks. Security promises stay in the core; detection and outputs are plugins.

client ─▶ Adapter ─▶ Admission ─▶ Defense modules ─▶ Enforcement ─▶ Provider ─▶ model │ Containment (shared state) ◀───┴───▶ Sinks (audit · alerts · metrics)

One configuration file

Providers, models, profiles, sinks, shared state, MCP servers and the egress proxy live in one agentshield.yaml, organized by profile. Deployment secrets and limits stay in environment variables; the file only names them. Unknown fields, modules, providers or models fail at startup.



  


  
  

    

      
Part 10 · Portability

      
The same design on any cloud

      
AgentShield's layers attach to roles in the architecture, not to AWS products. Swap each AWS service for its counterpart and the layers stay where they are. Claude is reachable directly from Anthropic on every cloud, or through the cloud's own model platform where it is offered.
